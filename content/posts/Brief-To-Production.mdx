Most products do not fail in the editor. They stall in the gap between a loose brief and a release someone can run.

I treat that gap as part of the job. The code matters. So does the path that gets it in front of users.

### Start with the outcome

A brief that lists screens is not a brief. I want the outcome first: who is blocked today, what they should be able to do next week, and what “done” looks like for the people who will operate the thing.

That is true for ecommerce, an admin tool, or an agent. If we cannot say who uses it and what changes for them, we are not ready to estimate.

### Scope is a conversation

I sit with stakeholders early. Not to collect a wishlist — to cut. What has to ship in the first release? What can wait? What is a nice demo that will rot if we build it first?

Agile is useful here when it is honest. Short cycles, visible work, and a backlog that can change without pretending the deadline did not. I would rather renegotiate scope than silently drop quality.

### Build the smallest system that can run

Once the outcome is clear I design the smallest path through the product: the screens, the API, the data, the one workflow that has to work on day one. Everything else hangs off that spine.

This is also where project management and engineering meet. If I am writing the interfaces and the services, I can see when a request is cheap, when it is a second product, and when it should wait.

### Release is part of the work

A feature that only lives on a laptop is unfinished. I stay for launch: environments, the first real users, the week after when support finds the holes.

That is the delivery I sell. Not a pile of tickets. A product a team can run.
